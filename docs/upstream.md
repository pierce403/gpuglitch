## Official Pico 2 W board identity

There is a hardware-family discrepancy at the Pico port's pinned revision. Its README groups the official Pico 2 W with RP2350B boards and its CMake configuration chooses that family by default. Raspberry Pi's SDK sets `PICO_RP2350A` to 1 for both the official Pico 2 W and Pico 2. A successful compile against a named board would establish neither electrical compatibility nor operation on that board. [Upstream board table](https://github.com/dalzyu/pico-ga100vfi/blob/e1ebd972f28ebd621c483a6c8d9f0ab69b3ba73c/README.md#L61-L69) · [Upstream CMake configuration](https://github.com/dalzyu/pico-ga100vfi/blob/e1ebd972f28ebd621c483a6c8d9f0ab69b3ba73c/firmware/CMakeLists.txt#L6-L28) · [Official Pico 2 W definition](https://github.com/raspberrypi/pico-sdk/blob/079c6f39023649b154152db30f1d781e884879bc/src/boards/include/boards/pico2_w.h#L24) · [Official Pico 2 definition](https://github.com/raspberrypi/pico-sdk/blob/079c6f39023649b154152db30f1d781e884879bc/src/boards/include/boards/pico2.h#L23)

## Integration decisions

- The PCI ID database installed on the review host (version 2026.02.12, `/usr/share/hwdata/pci.ids`) labels both `10de:2082` and `10de:20c2` as GA100 CMP 170HX. It assigns neither a stock memory variant. Record subsystem IDs, board identifiers and driver-reported capacity as separate observations. [PCI ID Project](https://pci-ids.ucw.cz/)
- Use passive OS discovery for the inventory. The Pico port's host tools include BAR access, sysfs restoration and an active serial control protocol. Its standalone detector actively probes a bus. Launching those utilities would exceed the scope of routine USB and PCI enumeration. [Pico port README](https://github.com/dalzyu/pico-ga100vfi/blob/e1ebd972f28ebd621c483a6c8d9f0ab69b3ba73c/README.md)
- Use ordinary driver and CUDA interfaces for workload measurements. Kate's register analysis concerns internal device state. Her experiment-loop directory describes pseudocode and historical examples. It supplies no general-purpose GPU acceptance test. [GA100VFI overview](https://github.com/kate-land/ga100vfi/blob/b71e3990cc652a07cdbb5c6d1192e3e8116692d2/README.md) · [Experiment-loop scope](https://github.com/kate-land/ga100vfi/blob/b71e3990cc652a07cdbb5c6d1192e3e8116692d2/glitch-loop/README.md)
- Capture a baseline per specimen. Kate reports different usable memory capacities even among nominal 8 GB cards and discusses how caching and address aliasing can produce misleading results. Record the driver-reported capacity separately from the byte range actually tested. PCIe and NVLink findings likewise require evidence from that card and host. [Author's results](https://blog.kate.land/posts/using-voltage-glitching-to-unlock-the-a100/)

## Post-Goldilocks publication boundary

The Pico CLI implements the glitch campaign and its checks. Kate describes `SENSE_CTRL`, shadowing secured-burn and write-security options, deriving FF records from each die's defects, and power cycling; her published repo has no general-purpose FF programmer or 80 GiB profile. The separate `ga100-ff-tools` project supplies an experimental FF planner and burner, but does not create the armed programming window or configure 80 GiB driver geometry. Kate also describes a separate U11 board change and host ROM check for NVLink, without a pin-numbered solder map or published ROM-bypass command. ## Published software memory route

At the reviewed cmpunlocker revision, [`install.sh`](https://github.com/amoghmunikote/cmpunlocker/blob/2c7e2ecd7944e791fec040d2680036beb4a9327b/install.sh) selects a 64 GiB target for PCI ID `10de:20c2` and a 40 GiB target for `10de:2082`. The `--profile` option changes a metadata label; runtime geometry follows the PCI ID. The gpuglitch command `ga100ctl memory-enable --source ../cmpunlocker --confirm` wraps this installer from a clean checkout at that commit. It selects a single supported NVIDIA GPU, records an operation event and passes `--no-iommu --no-gen2-service --no-passthrough`.

The suppressed installer features are IOMMU kernel-command-line setup, installation of a new early-boot Gen2 retrain service, and VM passthrough setup. The installer still removes conflicting NVIDIA DKMS modules, builds and installs patched NVIDIA modules, writes `/etc/modprobe.d/cmp-pcie-gen2.conf` with NVIDIA Gen2 options, and removes legacy PCIe retrain helpers. It may fetch matching NVIDIA source. A successful invocation requires a full card power cycle before measuring driver capacity and tested readback. The 64 GiB and 40 GiB values are targets, not guaranteed usable capacities. This software route does not burn FF records, expose a published 80 GiB profile, or establish NVLink operation. [Installer source](https://github.com/amoghmunikote/cmpunlocker/blob/2c7e2ecd7944e791fec040d2680036beb4a9327b/install.sh) · [Method and limitations](unlocking.md#published-software-memory-route)

## Experimental permanent FF route

The pinned `ga100-ff-tools` source offers a normal `10de:20c2` raw baseline capture, per-card `ffplan.py3` planning, and logical replay simulation. Select `--changes memory` for the documented FBIO, FBPA, FBP and ROP/L2 masks; the planner's default also selects compute and an experimental Gen3 candidate pair. The plan requires captured defect values, two matching full physical-row passes and an observed FF/IFF boundary. It preserves unrelated bits and allocates blank FF append rows from that card's evidence. Its optional `ffburn.py3` has offline review, non-programming live preflight and explicit `--execute-plan PLAN_ID` programming with three interactive confirmations. The upstream [agent workflow](https://github.com/kprinssu/ga100-ff-tools/blob/04573c9dbf82997fb481f26769ec58dc625d8318/AGENTS.md) reserves live burns for a human operator. No real GPU has validated the burner; its tests use injected I/O. [Planner](https://github.com/kprinssu/ga100-ff-tools/blob/04573c9dbf82997fb481f26769ec58dc625d8318/README.md#plan-and-simulate) · [Burner](https://github.com/kprinssu/ga100-ff-tools/blob/04573c9dbf82997fb481f26769ec58dc625d8318/BURNER.md)

The gpuglitch `memory-ff burn` command invokes that pinned external burner for an exact public memory plan and leaves its human TTY confirmations intact. The burner accepts live PCI identity `20c2` or glitched `2080`, not `2082`. It checks DSOV=0, fuse-program enable=1, secured-burn feature=0, software override=1 and open write privilege masks, but does not issue `SENSE_CTRL`, arm those registers, maintain the glitch state, control an external programming supply or configure framebuffer geometry. Thus a successful Pico campaign alone does not qualify the card for burning, and a verified FF row is not proof of 80 GiB usable memory after a cold boot. [Live preflight and limitations](https://github.com/kprinssu/ga100-ff-tools/blob/04573c9dbf82997fb481f26769ec58dc625d8318/BURNER.md#live-preflight)
